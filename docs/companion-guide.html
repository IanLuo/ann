Working with ann — the project companion

operating guide · grounded in the ann journey (27/27 legs) and the E2E review · v0.2 — revised after the first annotation pass

companion roles: assistant · memory · project manager · form: one CLI, local-first, per-project journey under <project>/.ann/ · status: draft — will evolve as we use it

The pitch, in ann's own words

Ann converts ambiguous human goals into a living chain of gated legs. "The product is the journey itself — plan, project memory, and observer in one. Structured data, not just markdown." Every step self-aware, human gates at each step end. It was built and managed through its own tree (the dogfooding invariant) — it is ready to be trusted with yours.

1 · What ann is — your three hats

  • Assistant — discusses the next step with you, not just reports it: it listens, researches, proposes, and feeds your feedback back in (journey, status, next, confirm, detail). It never assumes: state is derived from the log, every fact traced to its source — and when it can't resolve, it asks.
  • Memory — everything you decided and produced lives in the log and the locked artifacts: intent, acceptance criteria, gate decisions, evidence, versions, shas. The memory is append-only and hash-checked — it can't silently drift.
  • Project manager — work is raised as gated tasks (contract = intent + acceptance criteria), every task stops at an entry grill and exit confirm gate, and nothing ships without your accept. Integrity reads (check, verify, validate) fail closed. The whole project is inspectable at any grain — project → leg → task → event → artifact (journey <id>, detail, branch) — so you can check the facts at whatever level you need.

2 · What it's good at (evidenced)

  • Gated decisions that can't be skipped. A task cannot advance past grill or confirm without your decision. Rejection → bounded rework from the artifacts + feedback, closed through the same gate.
  • A memory that can't drift. The log is append-only with a write-rev ledger (hashes match files byte-for-byte). verify reconciles the log's claims against filesystem/git reality — it caught a real lockSha-vs-content mismatch on this very project that no other command could see.
  • Deterministic derived state. Status, gate cards, and run-next proposals are computed from the event tail, never remembered or assumed. Two sessions see the same truth.
  • Read/write discipline enforced by the CLI. Reads are bare; every write must end in ! — a bare write is refused with a hint. The naming is a guarantee, not a convention.
  • Artifact ownership + versioning. Producers own real files under their own artifacts/; lock! is a thin record over that file (name, path, type, version, and a recomputable sha). There is no docs/ layer to maintain. The deliverable is verifiable, not claimed.
  • A self-contained integrity loop. check (gates + traceability + hashes) · validate (rules) · verify (drift). Three independent reads that all agree before you call anything done.

3 · What needs work (evidenced — the honest gaps)

  1. No native correction flow — and none is needed as an edit. A finished task is finished: correcting it means a new corrective task that supersedes/amends the old one (ann's own immutability invariant), never a rewrite of the event. What's missing is engine support to spawn a correction bound to the task it corrects and close it through the record. The manual events.jsonl hand-edit on this project was a workaround that shouldn't exist.
  2. Gate accepts record no rationale. Every accept in the E2E wrote only accepted (claude). The why matters for a companion memory — capture it at every gate (grill and confirm).
  3. completed is not enforced as terminal. A completed task should be frozen: any later event (like an artifact-locked backfill) must be refused. Reopening is a correction task, not an append. This is the #1 integrity fix.
  4. Record-type artifacts carry no doc — the event is the record. The thin collapse generalized this to every artifact: the producer's file stays in its own artifacts/ and the artifact-locked event payload carries path/sha/type. There is no docs/ layer — the collapse retired it — so the old symlink-dangle hygiene item is closed, not pending.
  5. Memory can be richer events, not a parallel store. Lightweight companion facts belong as event payloads — more event kinds (or payload-carrying appends), each hashed into the ledger, rather than a separate notes surface.
  6. The tool can't stop a sloppy driver — and shouldn't gate every action. The fix is enforcement where the tool can (terminal freeze, required lock before confirm, one-writer) plus a review gate at meaningful boundaries (leg close, release) and a pre-confirm checklist (check + verify + hygiene rules) — not a gate per keystroke.
  7. No structured scope language. Ratios like "5 done, 1 in progress" (the E2E's own shape) can't be expressed in the contract — scope is prose, not data, so there's no way to ask "is this leg's scope proportionate?" It needs a concrete use case before we design it; deferred.

5 · How to work with it — the operating rhythm

  1. The daily loop. journey → where we are · status → every node's state · next → what's runnable now · check → is the world coherent. Read first, act second.
  2. Raise work as contracts. spawn! a task with intent + testable ACs. Write ACs like the mdsh 5 — each one checkable by an executable run, not by vibes.
  3. The gate loop — the heart. confirm <id> (read the card: intent · ACs · artifacts · gates) → submit! <id> grill → re-read → gate! <id> grill accept "<rationale>" — record the why, not just accept. The grill also decides the shape of the next step (see §6). Then do the work.
  4. Produce and lock the real deliverable. Write the actual file under the task, then lock! it — lock the code/artifact under its own name, not only its doc. Evidence the run that proves the ACs.
  5. Close through the exit gate. submit! <id> confirm → gate! <id> confirm accept. Commit only after exit acceptance. No backfills, no post-close locks — once completed is appended, the task is frozen.
  6. Hygiene is non-negotiable. Run check + verify before calling anything done. Never hand-edit events.jsonl/node.json. When the log is wrong, raise a corrective task — the tool grows, the record stays true.

6 · Best patterns — what we've learned works

  • Small, grillable slices. One verifiable outcome per task; a task you can't grill is a task you haven't understood. At each advance point the grill decides the shape of the next step: is it a task or a leg — and how many? That is a decision, not a default.
  • Verify as you go — with an AC collector. Record each AC's pass/fail and its evidence (the actual run) as structured data, so "done" means "every AC checked," not "looks right." The E2E's 5/5 PASS came from actually executing the converter — make that the normal shape of proof.
  • Rationale at every gate. The memory is only as good as the why on the record. A decision without its reasoning is a future regret.
  • Let derived reads drive decisions. When a decision is on the table, the related context should already be at hand — the gate card and context packet (confirm, packet) — so you never decide blind.
  • Resolve, don't guess. When something is ambiguous: derive → probe → infer (labeled) → ask. Never silently invent.
  • Change the tool, not the log. When ann blocks a legitimate move, that's a bug in ann — fix ann, don't hand-edit the record.

7 · Dogfooding on your real project

The pact

From now on, this project is managed through ann, the same way ann was built through ann. Every session starts from the derived truth, every decision passes a gate, every deliverable is locked, and every friction becomes an improvement.

  1. Register the project. project! add <path> — each project carries its own journey.
  2. Seed the journey. Spawn the real goal as 01-goal with intent + ACs, then break the first leg into grillable tasks.
  3. Keep the companion cadence. Start each working session with journey / status / next; decide at gates with rationale; lock work as it lands; end the day with check + verify.
  4. Run the improvement loop. Every friction we hit is a candidate change to ann — the correction flow, gate rationale, the AC collector, richer event payloads. We track these as our next ann tasks. First sprint is the three log-protectors: terminal freeze, gate rationale, native correction flow.
  5. Review before trusting. When ann's E2E drive shipped, an independent review (read-only, actually ran the artifacts) was what surfaced the gaps in §3. Keep that habit: verify the tool's claims before extending them.

8 · Start today — three actions

  1. Register your real project: project! add and confirm with project.
  2. Seed the goal: spawn 01-goal with intent + ACs written to be executed.
  3. Walk one real task through the full loop — grill, work, lock, confirm — and note the first friction we hit. That note is our first ann improvement.
