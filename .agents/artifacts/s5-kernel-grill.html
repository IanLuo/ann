Grill: task 08 — the Planner Kernel (S5) · the lifecycle decision tree

Task 08-s5-planner-kernel — orchestrates the node lifecycle per flow-control (spawn → materialize → GATE① → validate → activate → execute → verify → GATE② → commit → look-back), frontmost-ready selection, bounded rework, flow config (step chains as data), provider adapter, spec expansion (F9). It is the missing middle layer the README flags: today the CLI does this orchestration directly. Below: the decision tree — annotate anything you'd change.

D1 — the kernel OWNS the lifecycle; the CLI delegates (FRONTIER) position: extract orchestration into a kernel API

Position: the kernel is a lifecycle API — materialize → validate → activate → execute → verify → commit → lookBack — that the CLI (and the future web surface) call. The CLI's ad-hoc direct store mutations move behind kernel functions. One orchestration, one owner, tested.

Alternative: leave the CLI as-is; kernel only adds what's missing (frontmost-ready/look-back as functions) — less churn, but the orchestration stays split.

D2 — flow config (step chains as data) position: ship the data + validation; minimal v1 consumption

Position: a rules/flow/ registry holds the step-chain templates (default: idea → validate → envision → spec → continue) + per-project overrides — data, validated, code never overrides. The kernel reads it to know a node's work-type/verify semantics. But v1 use is minimal — agents still propose nodes; the chain isn't auto-followed yet.

Alternative: defer flow config entirely (the chain is implicit until autonomous spawning exists) — less machinery now.

D3 — spec expansion (F9) position: build it, fake-adapter tests, live run deferred (no provider)

Position: the kernel owns F9 — detailed specs from the vision artifact (same honesty layer as the engines). Build + test with a fake adapter; the live run defers until a provider exists (consistent with the deferred dogfood).

Alternative: defer F9 entirely until providers exist.

D4 — frontmost-ready + look-back as kernel functions position: formalize (F5 "run next" primitive), consuming the S3 packet

Position: kernel.frontmostReady() (prefix order, failed/superseded skipped — already in the store's activate rule) and kernel.lookBack() (where we are + what's ahead, grounded) as tested functions; the CLI's journey delegates; the proposal can include the S3 packet summary.

D5 — bounded rework (AC3) position: the kernel owns the loop; 3 rejections then escalate

Position: formalize the rework loop — GATE① reject → re-materialize; GATE② reject → re-execute (or escalate to GATE① if the approach is invalidated); bound 3 per gate then escalate to a human design decision. The CLI's gate! delegates to the kernel.

D6 — the provider adapter AC5 is ALREADY BUILT position: the kernel's job is the WIRING — per-task model selection (the G2 seam)

Position: task 05 shipped the adapter (multi-provider + per-task model + retries + fail-closed). What's missing is the seam from the provider review: a task's declared model/provider → the engine/adapter call. The kernel resolves a node's model spec (contract/config) and passes it to engine calls.

D7 — the kernel composes what's built position: packet (S3) + validators (S4) + engines (S2) + adapter

Position: materialize = assemblePacket; validate = runValidators on the node; execute = route the work-type to the right engine (grilling/envision/spec) with the adapter; commit = gate-checks + the single-writer append. The kernel is the composition layer over the four built slices — no new machinery.

D8 — the CLI refactor risk position: incremental, byte-compatible

Position: migrate the CLI's spawn/gate flows onto kernel functions incrementally — pure kernel functions first (tested), then delegate; keep journey/status/check output byte-identical (the existing 129 tests + data-parity guard).

Resolve the frontier

D1 first: does the kernel take over orchestration (CLI delegates), or stay additive? Then D2–D8. My confidence: high on D1/D4/D6/D7 (they follow the design's ownership + the built slices); D2/D3/D8 are judgment calls (flow-config scope, F9 timing, refactor appetite).
