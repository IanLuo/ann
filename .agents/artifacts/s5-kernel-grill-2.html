Grill round 2: the Kernel as a thin STEP-EXECUTION framework (S5)

Incorporating round-1 feedback: the kernel is small, tight, modular, loosely coupled — interface protocols that modules implement. Steps are independently implemented and reorderable; a common Step structure lets the chain be data (create steps dynamically). Each step's execute has one or more executor kinds (command · tool · request · LLM) — the provider sits above the step, injected into execute. The CLI is NOT in the kernel — the kernel exposes functions that assemble the execute of each step; the CLI calls them. Below: the refined architecture + the round-2 decisions. Annotate anything you'd change.

R2-D1 — the Step protocol position: a step = id · kind · declared inputs · execute(ctx) — the ctx carries the injected executors

Position:

interface Step {
  id: string;            // 'validate' | 'envision' | 'spec' | …
  kind: 'grilling' | 'envision' | 'spec' | 'planning' | …;
  inputs: string[];      // DECLARED input deps (for chain validation + the packet)
  execute(ctx: StepContext): Promise<StepResult>;
}
interface StepContext {
  packet: ContextPacket;                 // the S3 materialized packet
  executors: { llm?, tool?, command?, request? };  // injected — the step picks what it needs
  artifact?: …;                          // upstream step outputs (vision → spec, etc.)
}

The step never knows the provider — it knows the llm executor interface. Loose coupling: a step written for llm works with any provider, any future tool, any surface.

Alternative: steps call engines directly (no ctx indirection) — simpler but couples steps to the adapter, blocking tools/mcp later.

R2-D2 — the EXECUTOR abstraction position: four protocols (llm · tool · command · request); v1 implements only llm — the others protocol-declared, unbuilt

Position: an executor = an interface each module implements; the kernel builds an executor set per step-run from the shared capability pool (the step-model decision: skills · tools · mcp are a shared dynamic environment, not predefined per step). v1 ships llm (wrapping the provider adapter — injected into execute). tool / command / request are protocol-declared and unbuilt — no consumers yet (same discipline as before: schema-ready, build when a consumer appears).

Alternative: build tool/command now — rejected (no consumer; framework-cleverness ahead of need).

R2-D3 — the dynamic chain (flow config as data) position: chain = a list of step ids; REORDERING validates input deps

Position: rules/flow/ holds the chain (default: idea → validate → envision → spec → continue) + per-project overrides — data, reorderable. A chain-validate checks reorderability: every step's inputs[] must be produced by an earlier step in the chain OR resolvable as a current artifact. Steps stay independently implemented; the chain is pure data.

Alternative: chain implicitly ordered by spawn prefix (status quo) — but then "adjust the flow dynamically" is impossible; rejected per your feedback.

R2-D4 — the kernel API surface position: functions the CLI + web call; the kernel never knows the CLI

Position:

kernel.frontmostReady()  // prefix order, failed/superseded skipped (F5)
kernel.lookBack()        // where we are + what's ahead, grounded (the journey review)
kernel.materialize(id)   // assemblePacket (S3)
kernel.validate(id)      // runValidators on the node (S4)
kernel.execute(id)       // find the node's step → build the executor set → step.execute(ctx)
kernel.verify(id)        // ACs + evidence
kernel.commit(id)        // gate checks + single-writer append (LB-3)
kernel.advance(id)       // the full lifecycle, with bounded rework

The CLI (and the future web surface) call these; the assembly of a step's execute lives in the kernel, not in the CLI.

R2-D5 — the existing engines become STEPS position: wrap, don't rewrite

Position: grilling + envision are tested engines (the honesty layer). They map onto the Step protocol as thin wrappers: a step's execute calls the engine with the llm executor (the injected adapter). The engines stay as-is — the protocol wraps them, no rewrite.

Alternative: refactor the engines into step-native code — churn on tested code, no benefit.

R2-D6 — task 08 scope position: Step protocol + executor interfaces (llm implemented) + kernel functions + flow config + step wrappers + F9 spec step + tests

Position: this is a BIG slice — but it's the one that makes everything after it mechanical (the web surface, autonomous advance, eval). The F9 spec-expansion step builds + tests with a fake adapter (live run deferred — no provider). Per-task model wiring lands here (the G2 seam: kernel resolves a node's model spec → injects it into the llm executor).

Alternative: split task 08 — kernel core now, flow-config + F9 later. Heavier ceremony; I'd keep one slice (they compose).

Round-2 verdict

Confirm R2-D1…D6 — especially R2-D1 (the Step protocol shape) and R2-D2 (executors: llm-only in v1), the two load-bearing ones. Everything else hangs off them.
