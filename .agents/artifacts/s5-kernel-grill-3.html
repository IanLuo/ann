Grill round 3: the Step model, refined (S5 kernel)

Round-2 feedback folded in: no `kind` — id distinguishes steps; what matters is the content of execute (it encapsulates the capability + the real work). Executors have their own protocol (they do the actual work) — and may be the place to emit events for the task. Step rules are better co-located with the step. The flow can be assigned to a task. The kernel calls abstract step functions; concrete instances implement them. Below: the round-3 decisions. Annotate anything you'd change.

R3-D1 — the final Step shape position: {id, inputs[], rules[], execute(ctx)} — no kind

Position:

interface Step {
  id: string;              // 'validate' | 'envision' | 'spec' | … — id only, no kind
  inputs: string[];        // declared input deps (chain validation + the packet)
  rules: RuleModule[];     // the step's OWN verify rules — CO-LOCATED (self-contained, per S4)
  execute(ctx: StepContext): Promise<StepResult>;   // the capability + the real work
}

`kind` is redundant — the id distinguishes; what the step IS is the content of execute. Rules live with the step (never an external rule.json — the S4 lesson).

R3-D2 — the EXECUTOR protocol + event emission position: executors are protocols that do the work AND emit; two-log trace

Position: an executor is an interface, injected into the step's ctx — llm · tool · command · request. Each operation returns a structured result {ok, result, provenance} and emits: the op-log always (runtime: what was called, timing, retries), evidence when the outcome is a task fact (a binding result, an answer, a produced artifact ref). This is the two-log trace made executable: executors are the emission points.

Alternative: the kernel emits centrally after the step returns — simpler but loses per-operation provenance granularity (the user's "executor is the place" is better).

R3-D3 — the kernel calls ABSTRACT step functions position: the kernel routes by id; concrete steps implement

Position: the kernel's contract is the abstract Step interface — it calls step.execute(ctx) (and the step's rules) via a step registry (id → implementation). The kernel never knows a concrete step's internals — steps plug in; the kernel stays transparent and small.

R3-D4 — flow assignable to a TASK position: project default chain + per-task override (node.contract.flow)

Position: rules/flow/ holds the default chain; a task's contract may declare its own flow (contract.flow: ["envision", "spec", …]) — an override, still chain-validated (each step's inputs produced earlier or resolvable). Different tasks can run different chains; the default applies otherwise.

R3-D5 — where verify semantics live position: in the step's co-located rules (already in R3-D1)

Position: a step's verify = running its own rules against the result + the ACs — the kernel calls them; the validators (S4) remain the whole-store check surface, the step's rules the per-step contract check. One rule class, two scopes — both self-contained.

R3-D6 — what task 08 builds now (final) position: Step protocol + executor protocols (llm implemented) + step registry + flow config (default + per-task) + kernel functions + grilling/envision wrappers + F9 step (fake-adapter) + tests

Position: one coherent slice — the framework + the two existing engines as steps + F9 (built, tested with a fake adapter; live run deferred). Tool/command/request executors stay protocol-declared, unbuilt (no consumers). Per-task model wiring (G2 seam) lands in the llm executor injection.

Alternative: split — kernel core now, flow-config + F9 later. I'd keep one slice (they compose); your call.

Round-3 verdict

Confirm R3-D1…D6 — the load-bearing ones are R3-D1 (step shape: no kind, co-located rules), R3-D2 (executor protocol as the event-emission point), and R3-D4 (flow per task). Then I accept the grill and build.
